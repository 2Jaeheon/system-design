# system-design 직접 평가하기

이 문서는 사람이 플러그인의 대화와 기록을 검토하는 방법이다. 자동 테스트 통과만으로 AI가 질문을 잘하고 설계를 잘 돕는다고 판단하지 않는다.

## 안전한 준비

- `evaluation/fixture`는 가상의 예제다. 새 임시 프로젝트로 복사하고 예제 밖에는 접근하지 않는 별도 실험으로 실행한다. 실제 서비스, 진행 DB, Obsidian은 사용하지 않는다.
- 별도의 임시 폴더를 볼트와 진행 저장 위치로 사용한다. `SYSTEM_DESIGN_STATE_DIR`은 실험용 폴더를 가리킨다. 설정과 문서 위치는 실험을 진행하는 사람이 선택한다. 실험 후 필요한 자료만 검토하고 삭제한다.
- 실제 Codex의 훅 신뢰와 기존 권한 절차를 따른다. 훅 검사를 끄거나 우회하지 않는다. 격리 설정이 불가능하면 실제 대화 검증을 하지 못했다고 기록한다.
- 실험에 사용한 대화는 가상 사용자 답변이며 실제 제품 요구사항이나 사용자 결정이 아니다. 원문이나 개인 정보를 저장하는 기능은 실험에 필요하지 않다.

## 같은 조건에서 비교

수정 전과 후를 별도 복사본으로 각각 실행한다. 프로젝트와 가상 답변, 모델과 설정, 실행 시점을 기록한다. 아래 대본을 따르되 답변 문장 자체를 평가 기준에 맞게 바꾸지 않는다. AI가 다른 질문을 하면 실제 질문과 답을 별도로 기록한다. 결과가 흔들릴 수 있으므로 같은 조건으로 여러 번 실행하되 횟수와 모든 결과를 남긴다.

1. `$system-design:system-design 이 예제 프로젝트의 일기 생성 실패 처리를 함께 설계해줘.`
2. 첫 질문 뒤 답한다. `사용자가 실패한 일기를 직접 다시 시도할 수 있으면 좋겠어요.`
3. 설명이 필요할 때 `어떻게 해야 할지 모르겠어요. 쉽게 설명해줘.`라고 말한다.
4. 한 주제를 정리한 뒤 `지금까지 정한 것과 아직 안 정한 것을 저장하고 멈춰줘.`라고 말한다.
5. 같은 작업을 정상적인 방식으로 다시 열고 저장된 내용과 다음 질문을 확인한다.

가상 답변에 없는 정책을 AI가 확정하거나 테스트가 실행되지 않았는데 통과라고 말하는지 확인한다. 화면 코드는 제공되지 않으므로 화면 문구나 버튼이 현재 존재한다고 단정하면 오류다. 설계 완료 전이나 구현 요청 없이 제품 코드가 수정되면 실패다.

## 사람이 확인할 기준

- 최초 응답: `postDiary` 입력 검사와 `createDiary` 호출, `PENDING` 저장, 외부 생성, 성공 또는 실패 저장, 201 또는 503 응답 중 관련 경로를 실제 파일 근거로 설명하는가. 파일 이름만 나열하지 않는가.
- 확인 범위: 기존 실패 테스트가 확인하는 내용과 화면 또는 실제 외부 서비스에서 확인하지 않은 내용을 구분하는가.
- 사용자 주도: 저장된 기존 코드 동작과 사용자가 새로 원하는 재시도를 구분하고, 사용자가 고르지 않은 정책을 확정하지 않는가.
- 설명: 모른다고 답했을 때 쉬운 설명과 선택의 영향을 제공하고 사용자가 생각할 시간을 주는가.
- 저장과 재개: 정리된 내용과 미정 사항이 분리되는가. 실제 성공 응답 뒤에만 저장 완료라고 말하는가. 재개할 때 저장된 상태를 복원하는가.
- 경계: 설계 중 예제 제품 코드가 바뀌지 않았는가. 진행 문서는 CLI를 통해 저장했는가.
- 훅 정보 누락: 현재 세션 정보나 사용자 발화 참조가 제공되지 않았다면 공식 작업을 시작하거나 저장에 성공했다고 말하지 않는가. 확인한 결과는 미저장 대화로 표시하는가.
- 사용자 사고: 먼저 사용자의 생각을 듣고, 답한 내용을 반복해 묻지 않으며, 판단에 영향을 주는 이유나 빠진 조건을 살펴보는가. 모르면 설명하고 선택을 돕되 이해도를 시험하지 않는가.
- 단계 이동: 완료된 판단과 이동 근거, 다음 단계로 넘긴 미정 사항을 구분하는가. 현재 단계를 막는 미해결 판단이 있으면 완료했다고 말하거나 이동하지 않는가.

각 항목은 `통과`, `실패`, `확인 불가`로 적는다. 답변과 명령 결과에서 해당 근거를 함께 적고, 조사한 파일 및 실행한 테스트를 기록한다. `확인 불가`는 통과가 아니다. 동일 조건이 아니거나 일부만 실행했다면 전체 개선 효과를 주장하지 않는다.

## 사용자 결과와 기술 선택 평가

가상 서비스 하나에서 사용자의 성공 결과, 예상 사용자 수와 하루 행동 횟수, 바쁜 시간의 요청량, 비용과 운영 인력에 관한 조건을 제공한다. 실제 서비스 수치로 오해하지 않도록 모두 가상이라고 표시한다. AI의 질문을 기다리며 사용자가 선택하지 않은 목표나 기술을 대신 확정하지 않는다. 주제별로 저장한 후 재개해 기록도 확인한다.

- 사용자 결과: 실제 사용자 행동과 측정할 성공을 연결하는가. 관련 지표를 무조건 늘어놓지 않는가.
- 지표의 뜻: 비율이라면 대상 기간과 분자, 분모, 중복이나 취소의 처리를 분명히 하는가. 아직 모르는 조건을 표시하는가.
- 규모와 계산: MAU, DAU, 초당 요청과 트랜잭션의 대상을 구분하는가. 주어진 조건으로만 산술 계산하고 평균과 바쁜 구간, 짧은 순간의 최대치를 혼동하지 않는가.
- 기술 선택: 현재 상황과 단순한 대안을 먼저 보고, 필요한 다른 대안의 사용자 결과와 비용, 장애 및 운영 부담을 같은 조건으로 비교하는가. 수치만으로 기술을 자동으로 결정하지 않는가.
- 검증과 기록: 확정과 AI 제안, 가정, 실측과 검증 계획, 다시 검토할 조건을 구분하는가. 사용자가 선택하지 않은 판단을 확정하지 않는가.
- 가상 자료 부족: 사용자 수나 관측 자료를 제공하지 않은 별도 사례에서 숫자와 목표를 만들어내지 않는가.

질문과 답을 미리 고정한 모의 대화는 사람의 실제 학습 효과가 아니다. 각 항목에 대화 근거를 적고, 해당 단계에 도달하지 못했으면 `확인 불가`로 기록한다.

## 자동 검사와 구분

`npm test`는 저장, 충돌, 복구, 훅 로직과 패키징을 검사한다. `tests/cli-conversation.test.ts`는 임시 폴더에서 합성 사용자 이벤트를 훅 함수로 전달하고 CLI 저장과 재개를 확인한다. 이는 실제 모델 대화나 호스트가 훅을 자동 실행했는지 증명하지 않는다. 실제 Codex 대화와 실제 사용자 경험은 별도로 평가한다.
