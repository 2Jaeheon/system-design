# 0.1.1 호출과 토큰 최적화

## 바뀐 동작

대화 중 추가 질문이나 설명은 저장 호출 없이 진행한다. 공개 방식, 실패 처리, 응답 시간 목표처럼 한 주제가 정리되면 `checkpoint` 한 번으로 요약과 문서, 필요한 ADR, 다음 질문, Obsidian 기록을 저장한다. 단계 종료 시 검토와 이동도 같은 저장에 포함할 수 있다.

기본 CLI 응답은 요약이다. 전체 상태는 `detail:"full"`로 요청한다. 평소 사용자 차례의 훅은 발화 참조와 최소 상태만 전달하며, 저장되지 않은 대화보다 오래된 질문을 반복 주입하지 않는다. 현재 단계 안내만 읽고 복구용 명령 안내는 필요할 때 읽는다.

저장되지 않은 내용은 대화 맥락에만 있다. 주제 종료나 명시적 중단 때 저장하며, 갑작스러운 맥락 손실 뒤에는 마지막 저장을 기준으로 재개한다. 사용자 참조 검증, 버전 충돌 검사, 문서 충돌 보존, 저장 실패 복구는 유지한다.

## 측정

오픈소스 [js-tiktoken](https://github.com/dqbd/tiktoken)의 `o200k_base`를 개발용 측정에만 사용한다. 라이선스는 MIT이며 배포 런타임에는 포함하지 않는다. 별도 AI API나 외부 압축 서버는 사용하지 않는다.

합성 예시에서 한 주제에 세 번 답한 뒤, 같은 최종 요약과 확정 ADR, 다음 질문, 개인 노트를 만드는 두 방식을 비교했다. 기존 개별 명령 방식은 12회, 새 주제 저장 방식은 1회다. 비교한 JSON 입력 토큰은 803에서 277, 응답 토큰은 6303에서 223으로 줄었다. 합계는 7106에서 500으로 약 93% 감소했다.

이 결과는 도구 통신 텍스트의 비교이며 실제 청구 토큰이나 전체 채팅 절감률이 아니다. 셸 실행 포장, 시스템 지시문, 모델의 답변과 내부 추론, 캐시 효과는 포함하지 않는다. 임시 경로, 임의 ID, 날짜, 해시는 정규화한다. 상태 응답과 훅, 스킬 안내의 별도 수치는 [측정 결과](token-benchmark.json)에 있다.

재현 명령:

```sh
npm ci
npm run benchmark:tokens
```

기존 스킬 안내 사본 경로가 있으면 `node scripts/token-benchmark.mjs /기존/skills`로 안내 길이도 비교할 수 있다. 원본 대화는 측정에 사용하지 않는다.

[RTK](https://github.com/rtk-ai/rtk)도 검토했지만 이 작업에서는 공통 명령 출력 압축보다 전용 CLI에서 불필요한 항목을 반환하지 않는 방법을 적용했다. 오류나 복구 정보가 일반 압축 과정에서 빠지지 않도록 전용 응답 형식을 유지한다. RTK 전역 설치나 셸 훅 교체는 하지 않았다.

## 비기능 요구사항

기존에는 첫 요구사항 단계의 `quality` 기준 안에 품질 목표가 있었다. 기능 범위 뒤에 품질 조건을 따로 정하는 단계가 없어 진행 순서가 불명확했다.

새 작업은 기능 요구사항, 비기능 요구사항, 핵심 객체, API, 전체 설계, 상세 검토, 설계 평가의 일곱 단계다. 비기능 단계에서 규모, 응답 시간, 장애와 데이터 보존, 접근 권한, 비용 순으로 필요한 조건을 구체화한다. 이 항목의 검토가 빠지면 다음 단계로 이동할 수 없다. 실제 측정이 아직 없을 때만 근거 항목을 검증 계획과 함께 보류할 수 있다.

기존 여섯 단계 작업의 순서와 문서 번호, 첫 단계의 `quality` 기준은 유지한다.

## 검증 범위

자동 검사 81개 통과. 묶음 저장의 사용자 발화 검증과 중복 실행 방지, 실패 시 문서와 상태 복구, 별도 비기능 단계의 완료 조건, 기존 작업 호환, 짧은 CLI 응답과 훅, 패키징을 확인했다. 스킬 공식 검사도 통과했다.

현재 호스트의 Node v26.3.0에서 검사했다. 패키지의 기존 지원 선언인 >=26.5.0 <27은 변경하지 않았다. 지원 선언 버전과 현재 실행 버전은 구분한다. Claude Code의 실제 대화 실행은 별도 검증하지 않았다.
