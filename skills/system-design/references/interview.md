# 단계별 인터뷰

질문의 목적은 사용자가 실제로 내리는 판단을 확인하고, 그 판단을 설계 조건으로 바꾸는 것이다. 현재 단계와 이전 답을 바탕으로 다음 질문 하나를 고른다.

## 먼저 사용자의 생각 듣기

단계의 목적을 한두 문장으로 설명한 뒤 열린 질문을 한다. 예를 들어 핵심 객체 단계라면 “이번 기능에서 구분해서 다뤄야 할 것은 무엇이라고 생각하나요?”라고 묻는다. 답변 전부터 특정 객체나 구조를 정답처럼 나열하지 않는다.

처음 요청에 이미 담긴 생각은 `start`의 `initialUserRef`로 연결한다. 같은 내용을 다시 말하게 하지 않는다. 그 생각은 실제로 말한 범위까지만 활용하며, 뒤에 한 질문의 새로운 답변으로 꾸미지 않는다. 앞서 나온 내용만으로 이번 판단을 정할 수 없다면 필요한 부분 하나를 확인한다.

## 암묵지를 구체화하는 질문

막연한 말을 발견했을 때만 아래 방법 중 필요한 하나를 사용한다.

질문하기 전에 이번에 결정할 내용과 사용자나 데이터에 생길 차이를 짧게 알려준다. 이미 답한 이유나 앞선 선택으로 알 수 있는 사실은 다시 묻지 않는다. 선택을 바꿀 수 있는 불확실한 근거가 있을 때만 그 부분을 물어본다. 사용자가 모르면 먼저 필요한 설명이나 작은 예를 제공하고 원래 판단으로 돌아온다. 질문은 이해도를 채점하거나 정답을 맞히게 하는 수단이 아니다.

- **실제 경험:** 최근에 그렇게 판단했던 일을 묻는다.
- **차이:** 좋은 결과 하나와 원하지 않았던 결과 하나를 비교한다.
- **근거:** 두 결과를 다르게 판단한 이유를 묻는다.
- **경계:** 조건 하나가 달라져도 같은 판단을 하는지 묻는다.
- **실패:** 일부 처리만 끝났거나 응답을 받지 못했을 때 기대 결과를 묻는다.
- **재검토:** 지금의 선택을 언제 다시 바꿔야 하는지 묻는다.

한 답변에 이 질문들을 모두 붙이지 않는다. 고정된 회차에 반대 의견을 꺼내지도 않는다. 설계에 영향을 주는 중요한 불확실성이 해소되면 그 질문을 끝낸다.

예를 들어 “수정한 내용을 보호해야 한다”라는 답에는 “아직 공개하지 않았더라도 사람이 수정했다면 보존해야 하나요?”라는 질문이 가능하다. 이는 예시이며 실제 사용자 정책으로 기록하지 않는다.

## 답변을 다룰 때

사실은 어디서 확인했는지, 결정은 누가 정했는지, 가정은 아직 무엇을 확인해야 하는지 구분한다. 사용자 답변을 다른 의미로 해석했을 가능성이 있으면 그 차이를 구체적으로 질문한다.

“제출됨”, “처리됨”, “보임”, “이해함”을 같은 상태로 다루지 않는다. 메시지를 보냈다는 사실은 상대가 읽거나 이해했다는 증거가 아니다. 프로그램이 정한 상태 검사도 사람의 판단 내용이 옳다는 증명은 아니다.

코드에서 확인한 현재 동작을 새 요구사항으로 자동 채택하지 않는다. 현재 동작을 유지할지는 사용자 의도와 함께 확인한다.

## 모르는 내용을 설명할 때

[쉬운 설명 규칙](explanation/guide.md)을 따른다. 실제 처리 순서를 작은 예와 그림으로 설명한 뒤 원래 질문으로 돌아온다. 사용자가 원하면 선택지와 추천 이유를 설명하되, 선택을 대신 확정하지 않는다.

기록에는 설명을 제공했는지, 사용자가 이해했다고 말했는지, 사용자가 자신의 말로 설명했는지를 구분한다. 이해했다고 기록하려고 별도 시험을 강제하지 않는다.

## 종료와 재개

사용자가 답하지 않았으면 질문을 대기 상태로 남긴다. 질문 수가 많아졌다는 이유만으로 불명확한 결정을 확정하지 않는다. 피로를 느끼거나 중단을 원하면 현재 상태와 다음 질문을 남기고 멈춘다.

단계가 완료됐으면 성공 응답을 확인한 뒤 이미 정한 내용과 해당 단계의 필수 기준을 충족한 근거, 다음 단계에서 다룰 미정 사항을 짧게 설명한다. 현재 단계를 막는 미해결 판단은 해결하기 전까지 이동하지 않는다. 아직 측정하지 않은 근거는 허용된 기준에 한해 구체적인 확인 계획과 함께 남긴다. 나중에 앞선 답을 바꾸면 영향을 받는 설계와 ADR을 연결해 다시 검토한다.
