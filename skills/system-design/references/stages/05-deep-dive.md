# 6. 상세 검토

이 단계에서는 처음 정한 품질 목표를 현재 설계가 만족할 수 있는지 살펴본다. 사용자가 가장 중요하다고 생각하는 지점 하나와 그 이유를 먼저 말하게 한다.

## 남길 결과

- 검토할 중요한 지점과 연결되는 품질 요구사항
- 단순한 안, 그 안의 한계, 가능한 개선안
- 선택한 안의 이점과 비용, 운영 부담, 포기한 보장
- 숫자 또는 구체적 실패 사례에 근거한 검토와 검증 계획

각 대안을 같은 조건으로 비교한다. 필요한 경우 사용자에게 보이는 결과와 완료 시간, 사용량과 비용, 실패 시 결과, 데이터 보존, 팀의 운영 부담을 함께 본다. 근거가 부족한 항목은 미확인으로 남긴다. 어떤 수치나 상황이 선택을 바꾸는지와 확인할 방법을 구체화한다. 다른 중대한 위험이 확인되면 이유를 설명하고 별도로 검토한다. 작은 변경에서 중요한 지점이 하나뿐이라면 다른 지점을 억지로 만들지 않고 그 이유를 기록한다.

실제 문제에 따라 동시 변경, 중복 요청, 느린 외부 서비스, 데이터 유실, 오래된 조회, 부하 집중 등을 살펴본다. 캐시, 큐, 복제, 샤딩을 모든 작업의 필수 구성으로 만들지 않는다.

실패 사례는 시간순으로 따라간다. 예를 들어 저장 후 응답 유실, 두 요청의 경합, 처리 중 중단을 구분하고 최종 데이터와 사용자 결과를 확인한다. 성공 경로만 보고 보장을 확정하지 않는다.

자원 추정은 계산 결과가 저장 방식, 대수, 처리 구조 같은 선택을 바꾸는 경우에 수행한다. 가정과 단위, 계산 범위, 실제 측정 여부를 함께 남긴다. 다른 서비스의 예시 처리량을 이 프로젝트의 측정값으로 쓰지 않는다.

## 완료 기준

- `priorities`: 중요한 지점을 품질 요구사항과 연결해 골랐다. 하나만 검토했다면 그 이유를 남겼다.
- `alternatives`: 단순한 안의 한계와 개선안을 비교했다.
- `tradeoffs`: 얻는 것과 감수하는 것, 다시 검토할 조건을 정했다.
- `validation`: 계산이나 사례의 근거와 실제로 검증할 방법이 있다.

측정 전이라면 검증 계획을 남긴다. 목표를 만족했다고 미리 표시하지 않는다.

## 정확한 용어와 검토

동시성, 실패 지점, 트랜잭션 경계, 일관성, 복구 중 실제 변경에 중요한 지점을 사용자가 하나씩 고르게 한다. 각 선택의 효과와 비용, 검증할 실험을 구분한다.
