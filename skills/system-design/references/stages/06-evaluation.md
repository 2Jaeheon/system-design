# 7. 설계 평가

이 단계에서는 처음 요구한 일과 지금의 설계를 대조한다. 사용자가 먼저 충분한 부분과 아직 걱정되는 부분을 설명하게 한다.

## 남길 결과

- 각 핵심 기능을 담당하는 처리 경로
- 각 품질 목표의 설계 근거와 검증 방법
- 미충족 조건, 아직 측정하지 않은 조건, 허용하기로 한 한계
- 고르지 않은 대안과 다시 검토할 조건
- 구현할 작은 작업과 각 작업의 완료 조건

구성요소를 도입했다는 사실만으로 요구사항 충족을 표시하지 않는다. 근거가 계산인지, 실험인지, 운영 측정인지 구분한다. API만 있고 처리 경로가 없는 기능도 남은 한계로 드러낸다.

중요한 사용자 결과에서 출발해 관련 지표와 사용 규모, 선택한 처리 방식, 비교한 대안, 검증 방법을 이어서 확인한다. 지표의 정의나 실제 측정이 없으면 미확인으로 남기고 확인할 방법을 적는다. 숫자를 계산하거나 기술을 선택한 사실만으로 사용자 목표가 충족됐다고 결론 내리지 않는다.

실제 서비스 변경이라면 배포 전 검증과 배포 후 사용자 결과 관측을 나눈다. 되돌리는 조건과 방법도 정한다. 비동기 데이터 변경은 코드만 되돌리면 이미 처리한 데이터도 복구되는지 확인한다. 이 계획이 배포 실행 권한을 자동으로 주지는 않는다.

## 완료 기준

- `traceability`: 기능과 품질 요구가 설계 및 검증에 연결돼 있다.
- `gaps`: 남은 한계와 중요한 미해결 판단을 구분했다.
- `revisit`: 고르지 않은 대안과 재검토 조건을 남겼다.
- `implementation`: 구현할 범위, 작은 작업, 완료 조건이 명확하다.

중요한 판단이 해결되고 필요한 검증 계획이 있으면 설계 단계를 마칠 수 있다. 운영 검증까지 끝났다는 뜻은 아니다.

`advance`가 구현 요청 대기 상태를 반환하면 확정한 설계 버전과 범위를 보여주고 멈춘다. 사용자가 구현 시작을 요청한 뒤에만 `implement`를 호출한다. 사용자의 요청 없이 제품 코드를 수정하지 않는다.

## 정확한 용어와 검토

기능과 품질 목표별로 설계 근거, 아직 확인하지 않은 가정, 검증할 조건을 연결한다. 추정치, 목표, 실측치와 테스트 통과는 각각 다르게 표시한다.
