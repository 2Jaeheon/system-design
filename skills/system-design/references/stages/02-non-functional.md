# 2. 비기능 요구사항

기능이 실제로 쓰일 때 지켜야 할 조건을 정한다. 기능은 무엇을 할 수 있는지, 비기능 요구사항은 얼마나 빨라야 하고 어떤 상황에서도 무엇을 지켜야 하는지에 대한 조건이다.

## 진행 순서

첫 질문은 사용자가 중요하게 생각하는 조건을 먼저 말하도록 한다. 이후 아래 순서로 하나씩 구체화한다. 질문을 한꺼번에 나열하거나 모든 주제에 같은 숫자를 강요하지 않는다.

1. **사용 규모:** 하루 사용자와 바쁜 시간의 동시 요청, 생성 횟수, 저장량을 확인한다. 목표와 실측값을 구분한다.
2. **응답 시간:** 일반 조회와 오래 걸리는 작업을 나눈다. 어떤 요청의 시작과 끝을 재는지, 목표 시간과 단위, P95 같은 기준, 측정 시간 구간을 정한다. 접수 응답과 생성 완료 시간은 다를 수 있다.
3. **장애와 데이터 보존:** 허용할 중단 시간, 복구 목표, 잃어도 되는 데이터의 범위, 중복 요청과 오래된 데이터가 허용되는 조건을 정한다.
4. **접근 권한과 개인정보:** 누가 어떤 데이터를 볼 수 있는지, 보존 기간과 삭제 조건을 정한다. 구체적인 인증 기술 선택은 뒤 단계에서 한다.
5. **비용과 우선순위:** 사용량이나 월 비용 제한, 속도와 비용 등이 충돌할 때 무엇을 우선할지 정한다.

주제 하나가 정리될 때 `checkpoint`로 저장한다. 한 답변에 조건이 충분하면 반복 질문하지 않는다. 모르는 숫자는 사용자가 정한 가정과 확인 방법으로 남긴다. 적용되지 않는 항목은 그 이유를 기록한다. AI가 제안한 수치는 사용자 목표로 바꾸지 않는다.

## 서비스 결과와 사용 규모 연결

기능 단계에서 정한 사용자 결과와 연결해 이번 설계에서 판단을 바꿀 지표를 소수만 고른다. 예를 들어 사용자가 원하는 결과가 완료되는 비율이나 완료까지 걸린 시간이 적합할 수 있다. 필요하면 지표마다 대상, 행동 또는 성공의 뜻, 분자와 분모, 측정 기간, 중복과 취소의 처리, 자료 출처를 함께 정한다. 분자나 분모가 없는 시간 지표는 측정 대상과 시작 및 종료 시점을 정한다. 자료가 없으면 확인 방법을 남기고, 실제 수집이나 외부 서비스 접근은 사용자의 범위와 권한을 따른다.

사용 규모는 사용자 수, 사용자당 행동 횟수, 요청별 읽기와 쓰기, 재시도나 외부 호출을 필요한 범위에서 이어서 계산한다. 사용자의 현재 상황, 운영 인력과 비용 제한도 설계 선택에 연결한다. 평균과 바쁜 시간의 관측 범위를 구분하고, 필요한 수치가 없으면 가능한 범위만 계산한다. 가정, 목표, 과거 측정 및 현재 실측은 서로 구분한다. 예시 수치나 AI의 추정을 사용자가 정한 목표로 바꾸지 않는다.

## 완료 기준

- `scale`: 대상 사용량과 시간 구간, 목표인지 실측인지가 명확하다.
- `latency`: 주요 요청의 측정 시작과 끝, 수치, 단위, 백분위와 측정 구간이 있다.
- `reliability`: 가용성과 데이터 보존, 복구 및 일관성에서 필요한 조건을 정했다.
- `security`: 접근 범위와 데이터 보호 및 삭제 조건을 정했다.
- `cost`: 비용 또는 자원 제약과 충돌 시 우선순위를 정했다.
- `evidence`: 조건별 근거와 가정, 측정 계획을 구분했다.

실측 전이면 `evidence`만 구체적인 검증 계획과 함께 `deferred`로 둘 수 있다. 품질 목표 자체가 미정인 것을 측정 보류로 처리하지 않는다. 해당 기능에서 중요하지 않은 항목은 억지 목표 대신 적용하지 않는 근거로 검토한다.

다음 전체 설계 단계에서는 이 목표가 각 구성요소 선택에 어떻게 영향을 주는지 확인하고, 상세 검토와 설계 평가에서는 같은 기준으로 검증한다.

## 규모 추정과 용어

- DAU (일간 활성 사용자 - 하루에 정의한 행동을 한 고유 사용자 수)를 쓸 때 행동과 기간을 함께 정한다. 하루 사용자 수와 총 요청 수는 같지 않다.
- MAU (월간 활성 사용자 - 한 달 동안 정의한 행동을 한 고유 사용자 수)는 DAU나 초당 요청 수와 다르다. MAU만으로 DAU나 요청 수를 확정하지 않는다.
- RPS (초당 요청 수 - 지정한 경계에 들어오는 HTTP 요청 수를 시간으로 나눈 값), TPS (초당 트랜잭션 수 - 정의한 업무 또는 DB 트랜잭션의 초당 완료 수), QPS (초당 쿼리 수 - 정의한 쿼리의 초당 실행 수)는 세는 대상이 다르다. QPS는 문맥에 따라 API 요청을 뜻할 수 있으므로 측정 대상을 밝힌다. 서로 자동으로 같다고 가정하지 않는다. PRS처럼 뜻이 불명확한 약어는 임의로 정의하지 말고 문맥을 확인한다.
- Peak (최대 부하 - 정한 관측 구간에서 가장 바쁜 동안의 요청량)는 평균과 다르다. 요청 구간, 초당 평균을 내는 단위, 지속 시간, burst (순간 급증 - 짧은 시간에 요청이 몰리는 현상)를 명시한다. 근거 없는 peak 배율을 사실로 쓰지 않는다.
- 읽기와 쓰기별로 일 요청 수를 구할 정보가 있다면 `일 요청 수 = 하루 사용자 수 × 사용자당 해당 요청 횟수`, `평균 RPS = 일 요청 수 ÷ 86,400초`를 계산한다. 재시도 및 외부 호출은 별도 가정으로 더한다. 사용자당 횟수나 peak 가정이 없으면 필요한 하나를 묻거나 예시라고 표시하고 임의 확정하지 않는다. 10명 동시 접속을 10 RPS로 바꾸지 않는다.
- Latency (지연 시간 - 요청을 시작해 결과를 받을 때까지 걸린 시간)와 Throughput (처리량 - 일정 시간 동안 완료한 요청이나 작업 수)을 구분한다. P95 (95백분위 - 측정값의 95%가 이 값 이하인 기준)는 모집단과 기간, 오류 취급 방식을 함께 적는다. 화면 표시 시간과 서버 응답 시간은 측정 경계가 다르다.
- Availability (가용성 - 정한 시간 중 서비스가 조건에 맞게 사용 가능한 비율), RTO (복구 시간 목표 - 장애 후 서비스를 복구하기까지 허용하는 시간), RPO (복구 시점 목표 - 복구 시점에 허용하는 데이터 손실 시간 범위)를 정의할 때 장애 발생부터인지 감지부터인지 명시한다. 백업 주기가 목표 충족을 보장하지 않으며 복원 시험이 필요하다.

각 수치가 서버 용량, DB 부하, 비용, 장애 대응 등 다음 결정에 어떤 영향을 주는지 간단한 실제 계산이나 사례로 연결한다. 전체 표를 매번 출력하지 않는다.
