# 3. 핵심 객체

이 단계에서는 기능에 필요한 개념의 이름과 뜻을 정한다. 무엇을 같은 것으로 보고 무엇을 구분해야 하는지 사용자가 먼저 설명하게 한다.

## 남길 결과

- 핵심 객체마다 이름과 이 기능에서의 뜻 한 문장
- 객체 사이의 관계와 소유자
- 구분해야 할 중요한 상태와 상태가 바뀌는 조건
- 범위 밖 기능 때문에만 필요한 객체의 제외 이유

객체는 핵심 기능의 의미에서 찾는다. 하나의 업무 대상과 그 처리 결과물이 언제 만들어지고 언제 사용할 수 있는지 다르면 구분할 필요가 있다. 이름이 비슷해도 수명과 책임이 다르면 같은 것으로 취급하지 않는다.

이 단계에서 모든 테이블 컬럼, 자료형, 인덱스를 정하지 않는다. 개념을 나눴다고 반드시 테이블이나 서비스를 따로 만들어야 하는 것도 아니다. 저장 방식은 실제 처리에 필요한 시점에 정한다.

## 완료 기준

- `definitions`: 핵심 기능에 필요한 개념의 이름과 뜻이 분명하다.
- `relationships`: 관계와 소유, 중요한 상태 차이를 설명할 수 있다.
- `boundaries`: 같은 이름의 의미 충돌과 범위 밖 객체가 정리돼 있다.

구현 용어를 외우는지 묻지 말고, 같은 개념을 서로 다르게 이해하는지 실제 사례로 확인한다.

## 객체를 깊이 검토하는 관점

Entity (엔티티 - 고유하게 구분하고 수명 동안 추적하는 대상), Value object (값 객체 - 개별 식별보다 값 자체가 중요한 개념), Relationship (관계 - 두 대상이 서로 연결되는 규칙)을 실제 기능에 필요한 때 설명한다. 관계의 소유자, 하나와 여러 개의 관계, 생성과 삭제 시점, 상태 전이, 중복 저장과 권한의 기준을 구체적으로 확인한다. 도메인 개념과 DB 테이블, API 응답을 같은 것으로 가정하지 않는다.

사용자가 말한 객체로 핵심 사용 사례를 따라가며 빠진 책임, 고유 식별과 유효 조건을 검토한다. 예외가 실제 범위와 관련이 없으면 생략하거나 다음 단계의 질문으로 보관한다.
