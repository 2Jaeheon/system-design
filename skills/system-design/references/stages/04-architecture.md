# 5. 전체 설계

이 단계에서는 요청 하나가 실제로 처리되는 흐름을 연결한다. 사용자가 핵심 호출 하나의 흐름을 먼저 설명하게 하고, 필요한 다른 호출을 차례로 더한다.

## 남길 결과

- 사용자 행동부터 요청, 검증, 처리, 저장, 응답까지 이어지는 그림
- 각 구성요소가 맡는 일과 주고받는 데이터
- 응답 전에 끝내는 일과 응답 뒤에 이어지는 일
- 주요 구성요소 실패 시 사용자에게 보이는 상태와 복구 방향

상자의 이름을 늘어놓지 않는다. 각 구성요소가 어떤 요구사항을 해결하는지 설명한다. 기존 구조로 가능한데 새로운 서비스를 자동 추가하지 않는다.

사용자 결과와 규모, 속도, 장애, 비용 및 팀의 운영 여건 중 이번 선택을 바꾸는 조건을 기존 처리 경로와 연결한다. 사용자가 먼저 방향을 말한 뒤, 적합하면 현재 구조 또는 단순한 안과 다른 대안을 같은 조건으로 비교한다. 각 안에서 얻는 것과 감수하는 것, 현재 근거와 미확인 가정을 설명하고 사용자의 판단을 돕는다. 의미 있는 대안이 확인되지 않으면 만들어내지 말고 확인이 필요한 이유를 남긴다.

비동기라고 이름을 붙인 것만으로 요청 경로의 의존성이 사라지지 않는다. 일을 어디에 안전하게 맡긴 뒤 응답하는지, 맡기기 전에 장애가 나면 무엇이 남는지 확인한다.

Mermaid 그림으로 요청과 데이터의 흐름을 표현하고 짧은 글로 해석한다. 서버 내부 클래스나 모든 컬럼은 이 흐름을 설명하는 데 필요할 때만 정한다.

가용성이나 지연을 계산하면 경로와 전제를 함께 적는다. 각 구성요소의 지연을 단순히 더한 값이 운영 p99를 증명하지 않는다. 장애가 독립적이지 않은데 가용성 곱을 일반화하지 않는다.

## 완료 기준

- `paths`: 핵심 기능의 경로가 사용자부터 저장과 결과까지 끊기지 않는다.
- `responsibilities`: 각 구성요소의 역할과 데이터 흐름이 설명돼 있다.
- `async`: 응답 시점과 이후 처리, 필요한 저장 보장이 구분돼 있다.
- `failures`: 주요 실패가 사용자에게 주는 결과를 설명했다.

## 정확한 용어와 검토

요청 경로의 역할과 동기 및 비동기 경계를 설명한다. 병목, 단일 장애 지점, 부하, 비용과 장애 전파를 요구사항에 연결해 검토한다. 구조를 늘리기 전에 단순한 대안과 한계를 비교한다.
