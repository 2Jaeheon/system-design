# 4. API

이 단계에서는 기능을 요청하는 방법과 그 결과의 의미를 정한다. 사용자가 먼저 필요한 호출을 생각하게 한다. HTTP가 아닌 명령이나 이벤트도 입력과 결과의 약속으로 정리한다.

## 남길 결과

- 핵심 기능별 호출과 필요한 입력
- 응답 또는 결과와 그 시점에 끝났다고 보장하는 일
- 요청자 확인과 권한 검사 기준
- 오류, 중복 요청, 응답 유실 후 재요청의 결과

접수 성공, 저장 완료, 처리 완료, 공개 완료는 다른 상태일 수 있다. 상태 코드나 이벤트 이름만 적지 말고 무엇이 완료됐는지 문장으로 쓴다.

사용자나 소유자의 신원은 신뢰할 수 있는 인증 문맥에서 확인한다. 요청 본문에 적힌 식별자를 권한의 근거로 그대로 받아들이지 않는다.

요청이 처리됐지만 응답만 사라질 수 있다. 같은 요청이 다시 왔을 때 중복 효과가 생기는지 확인한다. HTTP 메서드 이름만으로 멱등성이 구현됐다고 판단하지 않는다. 필요한 요청 키와 결과 조회 방식은 실제 계약으로 정한다.

## 완료 기준

- `coverage`: 핵심 기능마다 필요한 호출이 있고 불필요한 범위 확장이 없다.
- `contracts`: 입력과 결과, 성공 시 보장하는 상태가 명확하다.
- `identity`: 요청자의 신원과 권한을 확인하는 기준이 있다.
- `retries`: 오류와 재요청 시의 기대 결과를 정했다.

기능을 바꾸는 성공 의미나 권한 판단이 남아 있으면 완료하지 않는다.

## 정확한 용어와 검토

Contract (계약 - 요청과 응답이 지켜야 하는 약속), Idempotency (멱등성 - 같은 요청을 반복해도 의도한 효과가 중복되지 않는 성질), authentication (인증 - 요청자가 누구인지 확인), authorization (인가 - 그 요청자가 이 행동을 할 수 있는지 확인)을 필요한 경우 예와 함께 설명한다. 응답 유실, 동일 키의 다른 입력, 권한 실패를 구분한다.
