# 1. 기능 요구사항

사용자가 할 행동과 서비스가 돌려줄 결과, 이번에 만들 범위를 정한다. 먼저 사용자의 생각을 듣는다. 이 단계에서 기술 제품이나 서버 구조를 고르지 않는다.

## 진행 순서

1. 기존 동작이 이번 판단에 영향을 준다면 [현재 흐름 조사](../current-flow.md)로 확인한 사실과 미확인 범위를 먼저 설명한다. 누가 어떤 일을 하려고 서비스를 쓰는지는 사용자에게 듣는다.
2. 핵심 행동과 결과, 공개 조건이나 실패 처리 같은 중요한 경계를 한 주제씩 정한다.
3. 이번에 만들지 않을 기능과 제외 이유를 정한다.
4. 기능 범위가 정리되면 저장과 검토를 묶어서 수행하고 비기능 요구사항으로 이동한다.

사용자의 핵심 행동이 정리되면, 그 행동이 사용자에게 성공했는지 어떤 결과로 확인할 수 있을지 함께 생각한다. 서비스의 목적과 이번 기능에 관련된 지표 후보만 다루고 숫자 목표는 사용자가 정하거나 이후 비기능 단계에서 검토한다. 이미 파악한 사용자와 성공 결과를 반복해서 묻지 않는다. 아직 모르는 지표나 수치는 미정으로 남긴다.

기능 문장은 “사용자가 무엇을 하면 시스템이 무엇을 돌려준다”로 쓴다. 속도, 규모, 가용성, 비용은 다음 비기능 단계에서 구체화한다. 이 단계에서 그런 이야기가 나오면 잊지 않도록 주제 저장의 남은 질문에 포함한다.

## 완료 기준

- `scope`: 대상 사용자, 핵심 행동과 결과가 분명하다.
- `exclusions`: 제외할 기능과 이유가 있다.
- `evidence`: 사용자 요구, 코드 사실, 가정과 확인 방법을 구분했다.

범위를 바꾸는 미해결 판단이 남아 있으면 이동하지 않는다. 새로운 일곱 단계 작업에서 품질 목표를 기능 단계 완료 조건으로 섞지 않는다.

## 기존 여섯 단계 작업

저장된 작업에 `non-functional` 단계가 없다면 기존 `quality` 기준도 필요하다. 그 작업에서는 기능 범위 다음에 비기능 안내의 순서대로 품질 조건을 정리한 뒤 핵심 객체 단계로 이동한다. 기존 단계나 완료 기록을 자동 변경하지 않는다.

## 기능을 깊이 검토하는 관점

사용자의 답변이 나온 뒤 Actor (행위자 - 기능을 사용하는 사람이나 외부 시스템), Use case (사용 사례 - 특정 목적을 달성하기 위한 행동), Scope (범위 - 이번에 다룰 기능과 제외할 기능)를 현재 예시에 맞게 설명한다. 공개 범위, 요청 전 조건, 정상 결과, 입력 제한, 실패와 재시도, 삭제와 보관 중 설계를 바꿀 내용을 선별해 살펴본다. 기능을 생략해도 되는 이유와 미정 사항을 구분한다.

질문 전에 사용자의 생각을 듣고, 답변 뒤에는 왜 중요한지와 빠뜨리기 쉬운 상황을 한두 가지 짚는다. 예를 들어 생성 성공과 공개 완료는 별도 결과다. 아직 말하지 않은 정책을 사용자의 결정으로 기록하지 않는다.
